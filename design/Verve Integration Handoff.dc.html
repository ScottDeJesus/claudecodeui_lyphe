Wiring the Verve console into your fork

This document lists everything the design prototype fakes, where each piece belongs in the repository, and what has to exist on the server before the screen can tell the truth. Work top to bottom: the theme layer first, then the stubs in priority order. Anything marked confirm is a guess about your setup that a five-minute look at the code will settle.

The prototype is a single design file. It is a reference for appearance and behaviour, not code to copy — it holds no API calls, no routing, and no state that survives a reload.

1 · Before you start

CloneFork, clone, npm install at the root, then run the dev server the repo's README names. The web app and the CLI bridge are one project — start both.
FontsInstrument Serif and Schibsted Grotesk load from Google Fonts. Self-host both if the console must run offline.
BranchWork straight on main in the fork. Land the theme layer first — every stub below inherits its tokens.
OrderTheme → tab visibility → file manager → git delegation → accounts and usage → CLI version awareness. Each step is shippable alone.

2 · Theme layer (no stubs, do this first)

The app already themes through CSS variables, so most of the reskin lands without touching component markup. Point the existing variables at Verve's tokens in src/index.css and tailwind.config.js, and alias the app's .dark class to Verve's .vv-dark block instead of maintaining a second palette.

--destructive--dangerDestructive and denied only — errors are amber
--radius--radius-input10px controls · 12 cards · 16 screens

Motion matters as much as colour. Verve's springs come from long durations on spring curves — copy tokens/motion.css and use --ease-enter for entries and hovers, --dur-move (0.45s) for transforms. Two traps we hit: the vv-anim helper sets transition … !important on every element, so apply it only for the half second around a light/dark switch, or it silently kills every transform transition in the app; and animate knobs and bars with transform, never left or width.

3 · Stub inventory

Six features are drawn but not real. Each entry names what the user sees, where it belongs, and what must exist behind it.

3.1 Workspace tab visibility

Smallest job

In the prototype: Settings → Tabs in the workspace → “Hide the Shell tab” and “Hide the Tasks tab”, both on by default; hidden tabs vanish from the workspace bar and a hidden active tab falls back to Chat.

To wire: two booleans in the existing settings store, read by the tab list in src/modules/project-workspace/WorkspaceTabs.tsx and by whatever guards tab content in WorkspaceMain.tsx. Persist with the other client settings (confirm whether that is localStorage or the server settings record).

Done when: hiding a tab never stops a running shell session or task sync — it only removes the tab.

3.2 Files: browse, preview, upload, download

In the prototype: the Files tab is no longer a code editor. It is a breadcrumb path, a listing with size and changed columns, “Up one level”, a drop zone, and a preview pane with three states — text excerpt, image with dimensions, and a dashed “No preview for this file” with Download. Upload shows a live progress row and confirms with a toast.

To wire: keep the tree from src/modules/file-tree/; replace the editor panel in src/modules/code-editor/ with the listing and preview. Server work: a directory listing that returns name, kind, byte size and mtime; a ranged read for text previews (first ~200 lines is enough); a thumbnail or direct read for images; a streaming download; and a multipart upload writing into the current directory. All paths must resolve inside the project root — reject traversal server-side, not in the UI.

Done when: unknown values render as an em-dash rather than 0, unpreviewable files offer download instead of an error, and an upload that fails says which file and why.

3.3 Git: agent-only commit and push

In the prototype: the panel is read-only — no commit box, no staging links, no pull. One button, “Push my changes”, starts a Sonnet conversation that runs /git, ticks four steps (read files → group into commits → write messages → push), ends itself, and lands on “✓ Pushed to main” with the commit hashes. The header badge and both file lists then collapse to a settled “Nothing waiting to be pushed”.

To wire: strip the write controls from src/modules/git-panel/GitPanel.tsx and keep its status read. The button spawns a session with the /git slash command, streams tool events into the four steps, and terminates on end-turn. The completion state must come from a real git status and rev-list @{u}..HEAD after the push, not from the agent's word. Failure cases the prototype does not draw and you will need: rejected push behind the remote, protected branch, no upstream, merge conflict, and credentials missing — each an amber banner naming the fix, with the receipt preserved.

Done when: the panel above the button can never contradict the result below it.

3.4 Account switcher and re-authentication

In the prototype: the sidebar footer opens a popover listing accounts — the active one with a ✓ and its conversation count, one flagged “▲ Signing in again is needed” with an inline Sign in, a signed-out Codex account with usage “—”, and “Add another account”. A small ▲ sits on the footer row whenever any account needs re-auth.

To wire: account records (id, provider, label, plan, credential state, last verified) plus a switch action. The contract the copy promises is the important part: switching changes only which account signs the requests — projects, conversations and running work stay put, and open conversations keep their history. Implement that by keeping session records account-agnostic, swapping the credential, and resuming each live session rather than re-creating it. Re-auth opens the provider flow and reports back per account; other accounts stay usable while one is broken.

Done when: a switch mid-conversation loses no messages, and a failed sign-in leaves the previous account active.

3.5 Usage meters

In the prototype: three bars in the account popover — the current five-hour window with its reset time, the week (amber past ~80%), and flexible spend as dollars against a cap, with a line explaining it is only drawn on once a limit is reached. The footer row shows the five-hour figure inline.

To wire: a per-account usage read, cached and refreshed on a timer, exposing fraction used, reset timestamp and — for flexible spend — amount and cap. Provider figures lag, so cache with the fetch time and say so, as the copy does. Amber is the near-limit state, not an error; red stays for denied. If a figure is unavailable the bar renders empty and the number is an em-dash — never 0%, and never a full bar.

Done when: a stale or missing reading is visibly unknown rather than quietly wrong.

3.6 CLI version awareness and session restart

New capability

In the prototype: conversations started on an older CLI carry an amber chip “↻ On CLI 2.1.3 · restart”; the sidebar footer summarises “Claude CLI 2.1.4 is installed · N conversations still run 2.1.3” with a restart-all action; and the chat shows a banner explaining that a conversation keeps the version it started with. Restarting stops the process and resumes the same conversation, history intact.

To wire — nothing like this exists today. The app's useVersionCheck only polls the console's own releases. You need: a claude --version probe at spawn, stored on the session record; the same probe for the installed binary, cached and re-read on a watch or interval; a comparison to mark sessions stale; and a restart that kills the process and re-spawns with --resume <session id> on the current binary. Restart mid-turn must be refused or queued, not silently dropped, and a resume that fails must leave the old transcript reachable.

Done when: the count in the footer, the chips, and the chat banner all derive from one comparison, and the notice disappears once no session is stale.

5 · Rules to preserve

These are not decoration — they are why the console reads as trustworthy, and they are easy to lose in implementation.

  1. Errors are amber. Red is reserved for destructive and denied.
  2. Colour never carries a signal alone. Every state also has a mark or a word: ● working, ✓ done, ▲ waiting for you.
  3. “We don't know” never looks like zero. A missing size, count or reading is a bare em-dash.
  4. Only positive evidence renders. Nothing is inferred from absence.
  5. Say what ran on its own. Anything automatic is labelled automatic; anything waiting says it is waiting for you.
  6. Plain English on screen. No token, flag or identifier reaches a label.

6 · Open questions

  1. Does the /git command already exist on your side, or does it need writing as part of this work?
  2. Should “Push my changes” be available per project only, or also across all projects with pending commits?
  3. Are multiple accounts per provider in scope, or one account each for Claude and Codex?
  4. Upload limits: maximum size, allowed types, and behaviour when a file already exists — overwrite, rename, or refuse?
  5. Should a stale-CLI conversation refuse to accept new messages until it is restarted, or keep running on the old version?
